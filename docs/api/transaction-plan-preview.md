# 거래 단위 월간 플랜 미리보기

`POST /api/plans/preview`는 로그인한 사용자의 보유카드, 거래내역, 최종 혜택 규칙을 읽어 **저장하지 않고** 월간 플랜을 계산한다. 기존 `POST /api/plans`와 `GET /api/plans`의 저장·조회 흐름은 이 PR에서 바뀌지 않는다. 화면에서 이 미리보기를 쓰려면 프론트엔드가 이 API를 호출해 결과를 연결해야 한다.

## 요청

```json
{
  "month": "2026-11",
  "asOf": "2026-11-10T12:00:00",
  "budget": {
    "total": 100000,
    "byCategory": [{ "category": "CAFE", "amount": 100000 }]
  }
}
```

이 JSON은 **형식 예시**이며 실험 결과나 팀원 거래가 아니다. `asOf`를 생략하면 서버 현재 시각을 쓴다. 과거 시연은 대상 월 안의 과거 `asOf`를 지정할 수 있다. 미래 시각과 다른 월의 시각은 받지 않는다. 예산은 기존 플랜 생성과 같은 `PlanBudget` 규칙으로 검증한다.

## 응답에서 화면이 쓸 필드

공통 `ApiResponse.data` 아래에 다음 값이 있다.

| 필드 | 의미 |
| --- | --- |
| `month`, `asOf`, `sourceMonth` | 대상 월, 계산 기준 시각, 예측 근거가 된 직전 달 |
| `historySpend` | 직전 달 업종별 실제 사용액 |
| `requestedBudget`, `effectiveBudget` | 사용자가 확인한 업종별 예산, 이미 결제한 금액이 예산을 넘은 경우 이를 반영한 계산 금액 |
| `forecast` | 직전 달 거래를 이번 달 같은 날짜·시각으로 옮기고 남은 업종 예산에 맞춰 금액을 조정한 거래 목록 |
| `strategies.HABIT` | 예전과 같은 카드 사용을 가정한 비교값 |
| `strategies.IMMEDIATE` | 결제 시점의 추가 혜택이 가장 큰 카드 선택값 |
| `strategies.CP_SAT` | 현재 결제와 다음 예상 결제 최대 2건을 같이 본 CP-SAT 선택값 |
| `selectedStrategy` | 예상 혜택이 가장 큰 전략. 동률이면 CP-SAT, 즉시 할인, 기존 습관 순 |
| `strategies.*.totalBenefit` | 이미 발생한 결제와 남은 예상 결제를 합친 월간 예상 혜택(원) |
| `strategies.*.allocations` | `userCardId`·업종별 목표 결제액과 예상 혜택. `userCardId`는 `GET /api/cards`의 보유카드 ID |
| `strategies.*.forecastAssignments` | 결제일 순으로 예상 거래마다 고른 보유카드 ID |
| `strategies.CP_SAT.optimal/feasible/fallback` | 각 결제에서 풀이 완료·시간 내 해·즉시 할인 대체가 나온 횟수 |
| `notes` | 초과 예산, 예측 및 미확인 조건의 한계 |

## 읽는 DB 데이터와 계산 범위

1. `user_cards`에서 분석 대상으로 선택되고 `card_products.id`에 연결된 보유카드를 읽는다.
2. `card_transactions`에서 **직전 달 1일 이상, `asOf` 미만**인 해당 사용자의 거래만 읽는다. 취소액을 뺀 금액과 사용자가 수정한 업종을 사용한다. 그 외 사용자의 거래와 `asOf` 이후 거래는 입력에 넣지 않는다.
3. `benefit_rules`와 `performance_tiers`에서 각 카드 상품의 `card-benefit-v1` 구조화 규칙을 읽는다. 선택한 카드에 미검증 규칙이 하나라도 있으면 일부 혜택만 계산하지 않고 `PLAN-007`을 반환한다. `stg_card_*`의 331종 원문·임시 데이터만으로는 거래 단위 혜택을 계산하지 않는다. 최종 테이블의 규칙이 카드사의 전체 혜택을 빠짐없이 담았는지는 원문과 별도로 대조해야 한다.
4. 전월실적 제외 여부가 DB 거래 필드만으로 확정되지 않으면 실적을 `null`(알 수 없음)로 둔다. CODEF 거래에 없는 제외 사유·매입 시각을 임의로 채우지 않는다. 따라서 해당 조건이 필요한 혜택은 0원 확정이 아니라 계산 불가로 남을 수 있다.
5. 직전 달 거래를 이번 달로 옮겨 남은 예산에 맞춘다. 이번 달 이미 결제한 거래와 카드 선택은 고정한다. 미래의 실제 결제를 안다는 가정은 하지 않는다. 예측에 없는 새 업종은 가맹점명을 비워 일반 예상 거래로 표시한다.

## 호출 전 확인

- 선택한 `user_cards.card_product_id`가 최종 `card_products.id`에 연결돼 있어야 한다.
- 해당 카드의 최종 `benefit_rules`에 `card-benefit-v1` 조건과 검증 완료 표시가 있어야 한다. 카드 목록 331종 적재 건수와 이 조건은 다르다.
- 직전 달 승인 거래가 있어야 한다. 없으면 `PLAN-008`, 계산 가능한 검증 규칙이 없으면 `PLAN-007`을 반환한다.
- 기존 `POST /api/plans`의 저장 결과와 이 미리보기 결과는 다른 계산 경로다. 화면 시연에서 둘을 같은 숫자로 표시하려면 BE·FE가 어느 경로를 사용할지 정하고 연결해야 한다.

실제 DB나 앱 화면의 끝에서 끝까지 동작은 이 문서와 단위 테스트만으로 증명되지 않는다. 공용 DB는 읽기 전용으로 확인하고, 데이터 수정을 하려면 담당자의 적재 절차를 따른다.
