# 거래별 혜택 계산 및 월간 플랜 재계산

## 적용 순서

1. 이 PR을 검토하고 백엔드에 반영한 뒤 Flyway `V32__add_per_transaction_max_to_benefit_rules.sql`을 적용해 `benefit_rules.per_transaction_max_krw` 컬럼을 추가합니다. 기존 값은 `NULL`이며 건별 최대 혜택액이 확인된 규칙에만 값을 넣습니다. `monthly_limit`은 월 전체 한도이므로 이 컬럼으로 복사하지 않습니다.
2. 운영 환경의 `BENEFIT_RULE_SELECTION`은 `READY_ONLY`로 유지합니다. `rule_engine_ready=false`인 규칙은 실제 추천 금액에 포함되지 않습니다. 승인 규칙이 0건이면 추천 결과도 0원이므로 데이터 검증과 승인은 별도로 진행해야 합니다.
3. 기존 API 주소와 요청·응답 형식은 유지합니다. 프론트는 `POST /api/recommendations/manual`의 `card.expectedBenefit`과 `POST /api/recommendations/chat`의 `recommendation.card.expectedBenefit`을 **지금 입력한 결제 한 건의 예상 혜택**으로 사용합니다. `GET /api/plans`와 플랜 상세의 예상 혜택은 **이번 달 거래 예상에 따른 월간 혜택**으로 구분해 표시합니다. 월간 혜택 일부를 사용자가 임의로 예약하거나 소진하는 입력은 보내지 않습니다.
4. 실제 카드 승인이 동기화되면 기존 `TransactionsChangedEvent` → `PlanRecalculationTrigger` → `PlanRecalculationService` 경로가 플랜을 다시 계산합니다. 추천 미리보기 호출은 DB나 플랜을 수정하지 않습니다. 결제 취소·환불과 업종 수정도 변경된 거래 스냅샷을 다시 읽어 반영합니다. 동기화 후에는 `GET /api/plans`와 `GET /api/plans/{planId}/changes`로 새 플랜과 변경 기록을 확인합니다. 별도로 플랜 생성·예산 수정 API에서 받은 `jobId`는 `GET /api/plans/jobs/{jobId}`로 조회합니다.

## 계산 변경점

| 경로 | 이전 | 변경 |
| --- | --- | --- |
| 결제 전 추천 | 카드·업종별 월 사용액에 가상 결제액을 더한 뒤 월 합계 혜택 차액 계산 | 승인 거래를 시간순으로 재생한 다음, 입력한 결제 한 건의 혜택을 계산. 건별 최소금액, 건별 최대 혜택액, 남은 월 한도, 공유 월 한도 적용 |
| 월초 플랜 | 업종 예산 합계를 카드에 배분 | 지난달의 개별 거래 금액을 사용자가 확정한 업종 예산에 맞춰 조정하고, 예상 거래 한 건을 한 카드에 배분. 예산 합계는 유지 |
| 월중 플랜 | 카드별 승인액을 고정하고 남은 업종 예산을 재배분 | 이미 승인된 거래와 그 혜택을 승인 순서대로 고정. 남은 예상 거래를 재배분하고 공유 한도 잔액으로 혜택 재계산 |
| 기타 거래 | 업종 합계에 따라 혜택 가능 | `ETC` 및 식별되지 않은 가맹점의 금액은 소비액에 포함하되 혜택은 0원 |

거래별 계산은 `TransactionBenefitService` → `SimpleBenefitCalculator.calculatePurchases` → `PurchaseBenefitMath` 경로입니다. 월초 예상 거래는 `PlanInputAssembler`와 `ForecastPurchaseBuilder`, 월중 재계산 입력은 `PlanRecalculationComputer`, 카드 배분은 `ForecastCpSatPlanner`가 담당합니다. 결제수단 전용·특정 가맹점 전용, 정액·마일리지, 대체 관계를 판정해야 하는 혜택은 현재 입력으로 확정할 수 없어 계산에서 제외합니다. `POINT` 비율은 기존 계산과 동일하게 수치로 합산하므로 현금과 다른 단위의 표시 정책은 별도로 확인해야 합니다.

## 연동 확인

1. 승인 규칙이 있는 보유카드로 1만 원 결제의 추천값을 확인합니다. 예를 들어 건별 1만 원 이상 20% 혜택이면 현재 결제 추천값은 2천 원입니다. 월간 플랜의 2만 원 예상 결제 혜택 4천 원과 서로 다른 값입니다.
2. 승인 거래 동기화 전후 `POST /api/recommendations/manual` 값을 비교하고, 동기화 후 플랜 재계산 작업과 변경 기록을 확인합니다. 같은 승인 거래를 중복 반영하지 않아야 합니다.
3. 환불 뒤 남은 월·공유 한도와 추천값을 확인합니다. 분류되지 않은 거래는 `ETC` 소비액에는 들어가고 혜택은 0원이어야 합니다.
4. 카드 상품과 규칙이 운영 테이블에 존재하고 `rule_engine_ready=true`인지 확인합니다. 스테이징 CSV의 행 수만으로 운영 추천 가능 여부를 판단하지 않습니다.
